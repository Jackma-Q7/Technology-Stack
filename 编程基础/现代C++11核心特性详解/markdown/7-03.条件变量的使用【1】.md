
## 条件变量(condition_variable)
&emsp;&emsp;条件变量也用来保护临界区，用于线程间的协作。在业务场景下，当线程工作的前提必须是共享资源满足某个条件时，通常会使用条件变量来实现

&emsp;&emsp;**就是线程间的相互通知，线程A操作完共享资源后，通知线程B**

&emsp;&emsp;它允许线程由于一些未到的条件而阻塞。它通常与互斥量结合在一起使用。这种方式用于让一个线程锁住一个互斥量，然后当它不能获得它期待的结果时等待一个条件变量(并释放该锁)，最后另一个线程会向它发信号，使它可以继续执行(获取锁)

&emsp;&emsp;C++ 11中的条件变量叫`condition_variable`，需要配合`unique_lock`使用

```cpp

#include <condition_variable>
#include <mutex>
#include <iostream>

std::mutex g_mxt;
//条件变量
std::condition_variable g_cnd;
//共享资源
int g_cnt = 0;

bool g_flag = false;
//void thread1Func()
//{
//    //std::lock_guard<std::mutex> lock(g_mxt);
//    while (18 != g_cnt)
//    {
//        std::this_thread::sleep_for(std::chrono::milliseconds(100));
//    }
//
//    std::cout << "g_cnt " << g_cnt;
//}
//
//int main()
//{   
//    std::thread thread1(thread1Func);
//    //std::lock_guard<std::mutex> lock(g_mxt);
//    while (1)
//    {
//        ++g_cnt;
//        if (18 == g_cnt)
//        {
//            break;
//        }
//    }
//
//    thread1.join();
//}

void thread1Func()
{
    std::this_thread::sleep_for(std::chrono::seconds(1));
    std::unique_lock<std::mutex> lock(g_mxt);
    while (!g_flag)
    {
        g_cnd.wait(lock);
    }
    
    //g_cnd.wait(lock, [] {return g_flag; });

    std::cout << "g_cnt " << g_cnt << std::endl;
}

int main()
{   
    std::thread thread1(thread1Func);

    while (1)
    {
        //std::lock_guard<std::mutex> lock(g_mxt);
        g_mxt.lock();
        ++g_cnt;
        if (18 == g_cnt)
        {
            g_flag = true;
            g_mxt.unlock();

            g_cnd.notify_one();
            break;
        }

        g_mxt.unlock();
    }

    thread1.join();
}
```

## 注解部分：
这段**注释代码**的结果大概率是：

```cpp
g_cnt 18
```

但它有一个严重问题：**数据竞争，结果不可靠**。

核心流程：

```cpp
std::thread thread1(thread1Func);
```

创建子线程，子线程一直检查：

```cpp
while (18 != g_cnt)
{
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
}
```

意思是：  
子线程每隔 100ms 看一次 `g_cnt` 是不是 18。

主线程这里：

```cpp
while (1)
{
    ++g_cnt;
    if (18 == g_cnt)
    {
        break;
    }
}
```

主线程不断把 `g_cnt` 加到 18，然后退出循环。

所以理想情况下：

1.  子线程启动，等待 `g_cnt == 18`
2.  主线程把 `g_cnt` 加到 18 
3.  子线程检测到 18 
4.  输出： 

```cpp
g_cnt 18
```

但是问题在这里：

```cpp
int g_cnt = 0;
```

`g_cnt` 是两个线程共享的普通变量。

主线程写：

```cpp
++g_cnt;
```

子线程读：

```cpp
18 != g_cnt
```

没有加锁，也没有用 `atomic`，所以这是**数据竞争**。

也就是说，虽然你经常看到输出 `g_cnt 18`，但严格来说程序行为是未定义的。

👉 两边的锁 **都被你注释掉了**

所以现在是：

+  子线程：直接读 g_cnt 
+  主线程：直接写 g_cnt 

➡️ **完全没有同步机制 → 数据竞争**

 如果你把锁打开，会发生什么？⚠️  

假设你改成这样：

子线程

```cpp
std::lock_guard<std::mutex> lock(g_mxt);
while (18 != g_cnt)
{
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
}
```

主线程

```cpp
std::lock_guard<std::mutex> lock(g_mxt);
while (1)
{
    ++g_cnt;
    if (18 == g_cnt)
    {
        break;
    }
}
```

👉 结果：**程序卡死（死锁/假死）**

 为什么会卡死？（关键理解🔥）  

执行流程：

1️⃣ 子线程先抢到锁  
2️⃣ 进入 while 循环  
3️⃣ 一直拿着锁 sleep

```cpp
while (18 != g_cnt)
{
    sleep...
        }
```

👉 ⚠️ **锁一直没释放！**

4️⃣ 主线程想加锁：

```cpp
std::lock_guard<std::mutex> lock(g_mxt);
```

👉 但是锁被子线程占着 → 主线程阻塞

5️⃣ 主线程无法修改 `g_cnt`

👉 子线程条件永远不成立

➡️ **死循环 + 锁不释放 = 卡死**

👉 **锁不能包住整个 while**

要这样写：

```cpp
void thread1Func()
{
    while (true)
        {
            {
                std::lock_guard<std::mutex> lock(g_mxt);
                if (g_cnt == 18)
                {
                    std::cout << "g_cnt " << g_cnt;
                    break;
                }
            }

            std::this_thread::sleep_for(std::chrono::milliseconds(100));
        }
}
```

👉 核心思想：

+  ✔ 只在“访问共享数据”时加锁 
+  ❌ 不要长时间持有锁（尤其是 sleep）

## 非注解部分：
这个版本**基本是正确的条件变量写法**，结果通常是：

```cpp
g_cnt 18
```

执行过程：

1.  子线程先睡 1 秒： 

```cpp
std::this_thread::sleep_for(std::chrono::seconds(1));
```

所以主线程大概率已经把 `g_cnt` 加到 18 了。

1.  主线程加锁修改共享数据： 

```cpp
g_mxt.lock();
++g_cnt;
if (18 == g_cnt)
{
    g_flag = true;
    g_mxt.unlock();
    g_cnd.notify_one();
    break;
}
g_mxt.unlock();
```

当 `g_cnt == 18` 时，把 `g_flag` 改成 `true`，然后通知子线程。

1.  子线程醒来后： 

```cpp
std::unique_lock<std::mutex> lock(g_mxt);
while (!g_flag)
{
    g_cnd.wait(lock);
}
```

这里很关键：

```cpp
g_cnd.wait(lock);
```

它不是一直占着锁等。

它会做三件事：

```cpp
释放锁 → 睡眠等待通知 → 被唤醒后重新加锁
```

所以主线程可以继续拿锁修改 `g_cnt`。

为什么这里要用 `while (!g_flag)`？

因为条件变量可能出现**虚假唤醒**。

也就是：即使没人真正通知它，它也可能醒一下。

所以不能写：

```cpp
if (!g_flag)
{
    g_cnd.wait(lock);
}
```

而应该写：

```cpp
while (!g_flag)
{
    g_cnd.wait(lock);
}
```

或者更推荐写成：

```cpp
g_cnd.wait(lock, [] { return g_flag; });
```

这句等价于：

```cpp
while (!g_flag)
{
    g_cnd.wait(lock);
}
```

你这段代码可以再优化一点：不要手动 `lock/unlock`，推荐用 RAII：

```cpp
while (1)
{
    std::lock_guard<std::mutex> lock(g_mxt);

    ++g_cnt;
    if (18 == g_cnt)
    {
        g_flag = true;
        g_cnd.notify_one();
        break;
    }
}
```

不过更严谨地说，`notify_one()` 可以放在解锁后：

```cpp
bool needNotify = false;

while (1)
{
    {
        std::lock_guard<std::mutex> lock(g_mxt);
        ++g_cnt;

        if (18 == g_cnt)
        {
            g_flag = true;
            needNotify = true;
        }
    }

    if (needNotify)
    {
        g_cnd.notify_one();
        break;
    }
}
```

一句话总结：

`mutex`**保护共享数据，**`condition_variable`**负责让线程高效等待某个条件成立。**

## 锁中if和while的区别？
一、结论先给你

👉 **必须用 while，if 是错误写法**

二、为什么？核心就一句话

👉 **condition_variable 可能“虚假唤醒”（spurious wakeup）**

也就是说：

👉 线程可能在**没有人通知的情况下自己醒了**

三、两种写法对比

❌ 写法1：if（错误）

```cpp
if (!g_flag)
{
    g_cnd.wait(lock);
}
```

问题流程：

1.  g_flag = false 
2.  线程进入 wait 
3.  ❗ 被“虚假唤醒”（或者被错误 notify） 
4. **不会再检查 g_flag**
5.  直接往下执行 

👉 此时 g_flag 可能还是 false

➡️ **逻辑错误！**

✅ 写法2：while（正确）

```cpp
while (!g_flag)
{
    g_cnd.wait(lock);
}
```

流程：

1.  g_flag = false → 进入 wait 
2.  被唤醒（不管真假） 
3.  再检查一次 `!g_flag`
+  如果还是 false → 继续 wait 
+  如果是 true → 正常执行 

👉 **保证条件一定成立才往下走**

四、你可以这样理解（非常重要）

👉 **wait 只负责“叫醒你”，不保证条件成立**

👉 **while 才负责“确认条件成立”**

五、最推荐写法（标准写法）

```cpp
g_cnd.wait(lock, [] { return g_flag; });
```

等价于：

```cpp
while (!g_flag)
{
    g_cnd.wait(lock);
}
```

👉 这是面试/工程里的标准答案

六、一句话记忆

👉 **if 是“等一次”，while 是“等到对为止”**

！！！！！！！虚假唤醒通常在这些情况下“更容易出现”：！！！！！！！！！

+ **多线程竞争激烈**
+ **使用**`notify_all`
+ **系统调度频繁**
+ **高并发程序**

**👉**虚假唤醒是操作系统允许的行为，发生时机不可预测，因此必须用 **while** 反复检查条件。

##  g_flag = true;不会直接跳过 while  吗？
子线程先跑

```cpp
while (!g_flag)
{
    g_cnd.wait(lock);
}
```

此时：

+  g_flag = false 
+  子线程进入 wait（睡眠） 

然后主线程：

```cpp
g_flag = true;
g_cnd.notify_one();
```

👉 子线程被唤醒 → 正常执行

✔️ 没问题
