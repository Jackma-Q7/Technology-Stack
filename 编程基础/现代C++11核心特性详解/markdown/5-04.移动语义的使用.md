## 移动语义的使用
&emsp;&emsp;移动语义是C++ 11 中非常重要的特性，整个C++ 98的标准库都已经为C++ 11彻底翻修过，目的是为那些类型移动的可以实现成比复制更快的类型增添移动操作，而且库组件的实现也已经完成修订以充分利用这些移动操作。似乎只需要将现有的代码通过支持C++11的编译器编译后，就享受到了移动语义带来的性能提升。但是实际情况并非如此：

&emsp;&emsp;编译器为自定义类型自动生成移动语义的是有要求的，必须没有声明复制操作，移动操作以及析构函数

&emsp;&emsp;即使在标准库中都已经支持移动操作，但是也可能不会像希望的那样带来那么大利好。这样取决已具体的实现

1. 比如list，它的实现通常是会在堆上分配内存，将容器元素放在这个堆内存上，内部只是会维护指向堆内存的指针。那么对list的移动，只算交换指针，那么效率自然会有提升
2. 比如array，它是C++ 11引入的新的容器类型，就是数组。它的内存就是对象内部的一个缓存区(比如是在栈上分配的一段顺序的空间)，所以对它的移动操作，还是要将元素进行复制

&emsp;&emsp;可见移动操作并非想象的多么便利，但是它的出现还是给我们提供了一个提升性能的机制，要充分利用移动语义，需要做到以下两点：

1. 在适合的场景，为自定义的类声明移动操作
2. 选择合适的容器类型(至少要知道容器特点，它的基本实现原理)来利用它的移动语义带来的性能提升

**一、移动语义到底在干嘛？**

👉核心目的：减少拷贝，提高性能

+  拷贝：复制一份数据（慢） 
+  移动：直接“拿走资源”（快） 

**二、为什么说“不是自动就变快”？**

 你原文说得很好，这里帮你翻译成人话👇  

❗1. 编译器不会随便帮你生成移动

👉 条件很严格：

+  不能写拷贝构造 ❌ 
+  不能写拷贝赋值 ❌ 
+  不能写析构 ❌ 

👉 但现实中：

👉 **你一旦自己管理资源（比如 new/delete），一定会写析构**

➡️ ❗ 那移动就不会自动生成

👉 所以：

👉 **实际开发几乎都要自己写移动**

❗2. STL支持移动 ≠ 一定更快

👉 关键看：**底层实现**

**三、容器对比（这段很关键）**

✅1. list（链表）

👉 内部：

+  每个元素在堆上 
+  容器只是指针链 

👉 移动时：

```plain
指针直接换
```

✔️ 非常快（O(1)）

⚠️2. array（定长数组）

👉 内部：

+  数据就在对象里面（连续内存） 

👉 移动时：

```plain
只能一个个拷贝
```

❗ 和拷贝几乎一样

🧠总结一句

👉 **能不能快，取决于“数据是在堆上还是对象内部”**

**四、怎么正确使用移动语义？**

你原文最后两点非常关键，我帮你强化👇

✅1. 自己写移动（核心）

适用于：

```cpp
class A {
    int* p;
};
```

👉 必须写：

```cpp
A(A&&); //=A(A&& t)
A& operator=(A&&);//=A& operator=(A&& t)
```

否则：

❗ 会退化成拷贝（甚至出错）

✅2. 选对容器（很多人忽略）

👉 想要移动快：

优先用：

+ `std::vector`
+ `std::string`
+ `std::list`

👉 避免误以为：

+ `std::array` 移动很快 ❌（其实还是拷贝） 

**五、再给你一个实际例子**

```cpp
std::vector<std::string> v;

std::string s = "hello";

v.push_back(std::move(s));
```

👉 发生：

+  不复制字符串 
+  直接“偷内部缓冲区” 

✔️ 很快

⚠️但如果是

```cpp
std::array<std::string, 3> arr;
```

👉 移动：

+  每个 string 还是要移动 
+  没有整体“偷一块内存”的效果 

🚀最终一句话总结（重点记这个）

👉 **移动语义不是万能加速器，只有“资源在堆上且可转移”的类型，移动才真正高效。**
