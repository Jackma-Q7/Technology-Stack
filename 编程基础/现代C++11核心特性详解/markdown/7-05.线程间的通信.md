## 线程间的通信涉及的两个问题
确保两个或更多的线程在关键活动中不会出现交叉(共享资源的竞争)

&emsp;&emsp;比如，在订票系统中的两个线程为不同的客户试图争夺最后一个位置

线程间保证正确的顺序(线程间的协作)

&emsp;&emsp;比如，如果线程A产生数据而线程B打印数据，那么B在打印之前必须等待

临界区

&emsp;&emsp;把对共享资源进行访问的程序片段称为临界区，可以通过互斥量和条件变量来保护临界区

&emsp;&emsp;**互斥量和条件变量是OS的同步原语（操作系统提供的最基础的线程同步工具）**

## 互斥量与锁
互斥量(std::mutex)

&emsp;&emsp;互斥量有两种状态，解锁和加锁。C++ 11提供了4种语义的互斥量:独占互斥量 std::mutex,带超时的独占互斥量 std::timed_mutex,递归互斥量 std::recursive_mutex，带超时的递归互斥量 std::recursive_timed_mutex

&emsp;&emsp;应该优先使用std::mutex，因为它满足我们所有的需要使用互斥的场景

```cpp
#include <mutex>
#include <thread>
#include <iostream>

int g_cnt = 0;
std::mutex g_mutex;
//std::lock_guard<std::mutex> lock(g_mutex);//RAII
void func(int c)
{
    for (int i = 0; i < c; ++i)
    {
        //g_mutex.lock();
        {
            std::lock_guard<std::mutex> lock(g_mutex);
            g_cnt++;
        }

        std::this_thread::sleep_for(std::chrono::milliseconds(1));

    }
}

int main()
{
    std::thread t1(func,100);
    std::thread t2(func,100);
    t1.join();
    t2.join();

    std::cout << g_cnt << std::endl;
}
```

结果稳定是：

```plain
200
```

原因：

`t1` 调用：

```cpp
func(100);
```

会让 `g_cnt++` 执行 100 次。

`t2` 也执行 100 次。

所以理论总数：

```cpp
100 + 100 = 200
```

而这里用了锁：

```cpp
{
    std::lock_guard<std::mutex> lock(g_mutex);
    g_cnt++;
}
```

`g_cnt++` 每次只能被一个线程执行，不会出现两个线程同时改 `g_cnt` 的问题。

这个 `{}` 很关键：

```cpp
{
    std::lock_guard<std::mutex> lock(g_mutex);
    g_cnt++;
}
```

离开 `{}` 后，`lock` 析构，自动解锁。

所以：

```cpp
std::this_thread::sleep_for(...)
```

是在锁外面睡觉，不会阻塞另一个线程太久。

一句话总结：  
**两个线程各加 100 次，因为加锁保护了 **`g_cnt++`**，最终结果就是 200。**

交替执行（并发）  

两个线程是这样的节奏：

```plain
t1: g_cnt++  (拿锁)
t1: 解锁

t2: g_cnt++  (拿锁)
t2: 解锁

t1: g_cnt++
t2: g_cnt++
...
```

👉 **每次加 1 是串行的，但整体是交替执行的**

## 问题1：
`g_mutex.lock()`;和`std::lock_guard<std::mutex> lock(g_mutex)`;一样的吗？

代码对比

```cpp
// 写法1：原始 lock()
g_mutex.lock();       // 手动加锁
g_cnt++;
g_mutex.unlock();     // 手动解锁 ✅ 必须写！
```

```cpp
// 写法2：lock_guard
std::lock_guard<std::mutex> lock(g_mutex); // 自动加锁
g_cnt++;
// 离开大括号 } 时，自动解锁 ✅ 不用写 unlock！
```

## 锁(lock)
`std::lock_guard`**： 最简单、安全的 RAII 锁，不可手动控制**

&emsp;&emsp;它只是对操作系统的锁的API进行RAII的封装，在构造时获得锁，在析构时释放锁(自动解锁)，并不提供额外的方法，也不提供lock和unlock方法。它是最简便的一种锁的封装形式

 `std::unique_lock`**：功能更强，可手动控制，适合配合 **`condition_variable`** 使用**

&emsp;&emsp;它除了对操作系统锁的API进行RAII的封装，还提供了手动控制锁的方法:`lock()`与`unlock()`。并且它提供了更多lock的策略，比如`try_lock`，`try_lock_until`等。配合信号量使用。

✅ 示例1：lock_guard（简单临界区）

👉 适合：只做“加锁 → 操作 → 解锁”

```cpp
#include <iostream>
#include <thread>
#include <mutex>

std::mutex mtx;
int g_cnt = 0;

void func()
{
    for (int i = 0; i < 100; ++i)
        {
            std::lock_guard<std::mutex> lock(mtx);
            g_cnt++;
        }
}

int main()
{
    std::thread t1(func);
    std::thread t2(func);

    t1.join();
    t2.join();

    std::cout << g_cnt << std::endl; // 一定是 200
}
```

👉 特点：

+  自动加锁/解锁 
+  无法手动控制 
+  最安全、最推荐 

🔥 示例2：unique_lock（必须用它）

👉 场景：**条件变量等待**

```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <condition_variable>

std::mutex mtx;
std::condition_variable cv;

bool ready = false;

void worker()
{
    std::unique_lock<std::mutex> lock(mtx);

    cv.wait(lock, [] {
        return ready;
    });

    std::cout << "Worker running\n";
}

int main()
{
    std::thread t(worker);

    std::this_thread::sleep_for(std::chrono::seconds(1));

    {
        std::lock_guard<std::mutex> lock(mtx);
        ready = true;
    }

    cv.notify_one();

    t.join();
}
```

❗ 为什么这里不能用 lock_guard？

如果你写：

```cpp
std::lock_guard<std::mutex> lock(mtx);
cv.wait(lock); // ❌ 编译都过不了
```

👉 因为：

`wait()` 需要做：

```plain
解锁 → 等待 → 被唤醒 → 再加锁
```

👉 lock_guard 不支持“解锁再加锁”  
👉 只有 `unique_lock` 支持
